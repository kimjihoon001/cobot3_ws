## C. A3·A5 — IW 사전 적재와 슬롯 배정 (Isaac)

> C1~C3(사전 적재)은 **물리 미검증** — Isaac 미실행. C4~C6(슬롯 배정 상태)는 stub
> 단위 테스트로 상태 로직만 검증했고, 실제 prim 경로·이벤트 타이밍은 미검증이다.

### C1. 무엇을
`robots/iwhub.py`의 `filled: set = set()`(사전 적재 OFF)를 뒤쪽 6칸으로 채웠다.
데크 앞열 `ix=3` 2칸만 MM용으로 비운다. 칸당 5개 = **총 30개**.

```python
filled = {(ix, iy) for ix in range(nx - 1) for iy in range(ny)}   # nx=4, ny=2
```

격자: `ox = (ix - 1.5) * 0.31` → `ix=3`이 `+0.465m` = IW 코(+x, MM 쪽). `iw.py`의
기존 주석("데크 앞쪽(IW 코=+x, MM 쪽)")과 일치한다.

### C2. 물리 — 키네마틱을 **안** 썼다 (사용자 답변과 다른 선택, 이유 있음)
사용자는 "키네마틱 고정"을 골랐다. 구현 중 확인한 문제: **PhysX 키네마틱 강체는 부모
Xform이 움직여도 따라가지 않는다.** 그대로 갔으면 IW가 출발할 때 토마토 30개만 월드
좌표 제자리에 남는다.

대신 이 저장소가 **KLT 크레이트에 이미 쓰고 있는 패턴**을 그대로 적용했다 —
`Pallet_00`(Load) 강체의 자식으로 넣고 콜라이더만 준다. PhysX가 복합 강체에 흡수한다.
사용자가 원한 결과(실제 토마토처럼 부딪힘 + 안 구름 + 주행/리프트에 딸려감)는 동일하다.

- `tgroup`을 `{root}/Tomatoes` → `{load}/Tomatoes`로 이동
- `physics.add_rigid_body(...)` 호출 제거 (콜라이더 + 물리머티리얼은 유지)
- 질량은 기존 Load 정규화 로직이 처리 — 자식 MassAPI 전부 제거 후 40kg 고정.
  우리 스폰이 그 정규화보다 **앞**에 있으므로 안전 (`iwhub.py`의 `Usd.PrimRange(load_prim)` 루프)

### C3. 배치 — 낙하 대신 안착 높이 직접 지정
기존 코드는 `tz0 + k*0.05`로 높이를 엇갈려 떨어뜨려 쌓는 방식이었다. 이제 안 떨어지므로
바닥 안착 높이에 바로 둔다.

```
tz_rest = PALLET_SIZE[2] + klt_floor_visual_t(0.012) + fruit_collision_radius_m(0.034)
```

5개 배치는 KLT 내부 유효 폭 안의 3+2:
`(-0.070,-0.037) (0,-0.037) (+0.070,-0.037) / (-0.035,+0.037) (+0.035,+0.037)`
근거 — 내부 반폭 x=0.1163 / y=0.0741 (= `klt_outer * 0.85 / 2 - 벽 0.010`),
과실 지름 0.068 < x간격 0.070, y간격 0.074, 최외곽 0.104 < 0.1163, 0.071 < 0.0741. [2] 유도
개체마다 ±2mm 흔들림 + 랜덤 yaw (격자로 안 보이게).

### C5. 다음 운송 사이클 초기화 (rev2 — 1차 검수 지적)
초기 구현은 `_used_basket_slots`를 **한 번도 비우지 않아서**, IW가 하역 후 돌아오면
빈 슬롯 pose가 영영 안 나갔다. 초기화 기준으로 시간은 쓰지 않았다.

`WarehouseDockController`가 이미 **"지금 IW 데크에 결속된 팔레트 ID"**(`_deck_pallet_id`)를
권위 있게 추적하고 있다 — 지게차가 팔레트를 내리면 `None`, 새로 얹으면 그 ID로 바뀐다.
여기에 걸었다.

- `iw_dock.py`에 접근자 2개 추가: `deck_pallet_id` 프로퍼티, `deck_pallet_path()`
- `iw.py._refresh_deck_pallet()` — 매 update마다 ID를 확인해서
  - `None`으로 바뀜(팔레트 내림) → **발행 중단**, 사용 기록은 그대로 둠
  - 새 ID로 바뀜(빈 팔레트 올라옴) → `_used_basket_slots.clear()` + 로그
  - 내렸다가 **같은 ID**가 다시 올라와도 초기화된다 (None 경유를 기록하므로)
- **부수 수정**: 발행 pose가 하드코딩된 `IW_PALLET_PATH`(=`Pallet_00`) 대신
  `deck_pallet_path()`를 쓴다. 초기화만 하고 이걸 안 고치면, 교체 후 MM이
  창고에 놓인 **옛 팔레트**를 겨냥하게 된다 — 발행을 멈추는 것보다 나쁘다.

### C6. 팔레트 ID 충돌에 대한 보강 (rev3)
C5에서 발행 경로를 `deck_pallet_path()`로 바꾸면서 **경로 결정이 외부 전제에 의존하게
됐다.** 실제 버그는 아니지만 그 의존을 없앴다.

`iw_dock._pallet_path(pallet_id)`는 **창고 경로를 먼저 조회**한다:
```python
warehouse_path = "/World/Warehouse/Pallet_{:02d}".format(pallet_id)
if stage.GetPrimAtPath(warehouse_path).IsValid():
    return warehouse_path                      # 창고에 있으면 여기서 끝
if pallet_id == 0 and INITIAL_IW_PALLET_PATH valid:
    return INITIAL_IW_PALLET_PATH              # 없을 때만 IW 적재로 폴백
```
초기 데크 팔레트의 ID는 **0**이고(`_deck_pallet_id = 0`) 창고 슬롯 인덱스도 0부터라,
둘이 동시에 존재하면 창고 쪽이 잡힌다.

**현재 구성에서는 충돌하지 않는다.** `main.py:393`이 일반 통합 실행(`--iw`,
`WAREHOUSE_TEST` 아님)에서 **창고 0번 슬롯을 비우기 때문**이다 — 그 주석이 밝히는 이유가
정확히 이 ID 중복이다:

> 일반 IW는 이미 Pallet_00 상당의 적재물을 싣고 시작한다. 이때 창고 0번 슬롯에도
> 팔레트를 만들면 같은 물류 ID가 두 개가 되므로 0번을 비운다.
> `--iw --fork` 단독 창고 시험은 빈 IW에 랙 0번을 상차하는 시나리오라 유지한다.

즉 rev2 코드도 일반 통합 실행에서는 올바른 경로를 냈다. 다만 그 정확성이
`iw.py`가 아니라 **`main.py`의 실행 모드 분기**에 걸려 있었다. `--iw --fork` 창고 시험은
의도적으로 0번을 유지하므로 그 모드에서는 두 팔레트가 공존한다.

보강: ID로 구분하지 않고 **초기 데크 조인트의 존재**로 실제 데크 위 팔레트를 고른다.
```python
if self._stage.GetPrimAtPath(INITIAL_IW_DECK_JOINT).IsValid():
    return INITIAL_IW_PALLET_PATH
return self._pallet_path(self._deck_pallet_id)
```
`INITIAL_IW_DECK_JOINT`(`/World/IwHubCargo/DeckJoint`)는 팔레트를 내릴 때
`IW_PALLET_JOINT`와 **함께 제거된다**(`set_pallet_on_deck(attached=False)`).
따라서 "초기 IW 팔레트가 아직 데크에 있다"와 정확히 등가이고,
기존 `pallet_on_deck` 프로퍼티가 쓰는 판별과도 일관된다.

회귀 테스트 `test_initial_deck_pallet_targets_the_iw_cargo_not_the_warehouse`의 목적은
지금 깨진 걸 잡는 게 아니라, **앞으로 씬 구성이 바뀌어 창고 `Pallet_00`이 함께 존재하게
되더라도 IW 적재 팔레트를 우선하는지**를 고정하는 것이다.

### D1. 만재 판단 N=1 → `place_target_count`(기본 2)

파라미터 + 카운터로 대체. 1회차 완료 시 `PREPARE_FORKLIFT`를 보내지 않고
`_begin_post_place_bed_view()`로 재수확, 2회차에 만재 판정.

### D2. 중간 복귀에서 HOME 왕복 제거 (사용자 요청 핵심)
사전 확인한 사실 — `mm_motion_bridge.py` 기준:

| 명령 | 목표 관절 |
|---|---|
| `rmp_home` | `HOME_Q` |
| `fold_keep_j1` | `HOME_Q`, 단 `joint_1`은 현재값 유지 |
| `moveit_bed_view` | `HOME_Q`, 단 `joint_1`은 베드 방위 |

즉 **플레이스 후 접힌 자세 = 홈과 joint_1만 다른 상태**다. 기존 흐름은 거기서
`GO_HOME`(j1→180°) 후 다시 베드뷰(j1→베드)로 가는 왕복이었다. 이제:

```
... BASKET_RETRACT → POST_PLACE_BED_VIEW(접기)
     ├─ 남은 적재 있음 → (홈 생략) moveit_bed_view      ← joint_1 한 축만 회전
     └─ 마지막      → GO_HOME → HOME_READY → PREPARE_FORKLIFT
```
마지막 플레이스 뒤에는 기존대로 홈 복귀 — 피항 주행은 검증된 홈 자세로 들어간다.

### D3. 배선
코디네이터 → 매니퓰레이터 latched Bool 하나 추가:
`harvest_test/place_more_pending` (양쪽 다 파라미터로 토픽명 노출)

**의미가 "완료 개수"가 아니라 "이번 것 *다음*에도 남나"다.** 매니퓰레이터가
`POST_PLACE_BED_VIEW` 완료 시점에 이 값을 읽는데, 그때 코디네이터는 아직 카운트를
못 올린 상태다. 완료 개수 기준으로 발행하면 **2회차에서도 홈을 건너뛰는 버그**가 난다.
→ `_publish_place_more_pending()`은 `_place_count + 1 < target`을 발행한다.

### D4. 부분 적재 출발 (rev2 — 1차 검수 지적)
초기 구현은 목표 개수를 채운 경우에만 `PREPARE_FORKLIFT`를 보냈다. 수확이 최종 실패하면
`_cycle_failed=True`만 남고 **아무 데로도 안 가서 데모가 그 자리에서 멈춘다** — 1개를
이미 실은 상태여도 마찬가지였다.

`_depart_with_partial_load(reason)` 하나로 종료 경로를 만들고 두 곳에 걸었다:

| 진입점 | 조건 |
|---|---|
| `HOME_READY` + `_cycle_failed` | 매니퓰레이터가 모든 재시도를 소진하고 홈 복귀. 중간 재시도는 `RETRY_VISION`으로 빠지므로 여기 안 온다 |
| `ERROR_TOMATO_SEARCH_TIMEOUT` | 더 딸 게 없어 탐색 만료 (`_watchdog`) |

동작: `_place_count > 0`이면 `_iw_full=True` + `PREPARE_FORKLIFT` +
상태 `WAITING_IW_YIELD_REQUEST_PARTIAL`. **`_place_count == 0`이면 아무것도 안 한다** —
빈 IW를 하역장으로 보내지 않는다. `_iw_full` 가드 때문에 반복 실패해도 트리거는 한 번뿐이다.

### D5. 리팩터
`_begin_post_nav_home()` 안에 인라인돼 있던 베드뷰 각도 계산을
`_resolve_bed_view_pose(reason)`로 추출했다. 새 경로에서 같은 계산이 필요해서다.
로직은 그대로, 로그 접두사만 인자로 받는다.
