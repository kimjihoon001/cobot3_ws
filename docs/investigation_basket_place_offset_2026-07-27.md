# 조사 보고 — 바스켓 릴리즈 80mm 보정의 정체

작성 2026-07-27 / 요청: Codex 지시(수정 전 원인·검증 결과 먼저 보고)
최종 갱신 2026-07-27 (실행 관찰 반영, rev2)

상태: **원인 확정.** `basket_place_toward_mm_m`은 사용자 지시로 0.08 → **0.04** 적용.
KLT 로컬 오프셋 교체는 **하지 않았다** — 전제가 틀렸음이 확인됐다(§2-4).

---

## 0. 결론 먼저

**80mm는 KLT 기하 보정이 아니라 스쿱 굴림(roll-out) 보정이었다.**

- 발행되는 슬롯 pose는 **KLT 콜라이더(=실제 바구니 내부)가 놓인 격자점 그 자체**다.
  prim 원점과 내부 중심이 8.4cm 어긋나 있다는 Codex의 1차 가설은 성립하지 않는다(§1).
- 그런데도 보정이 필요했던 이유는 **낙하점 ≠ 릴리즈점**이기 때문이다. 스쿱이 1/4구
  곡면이라 열리면 과실이 곡면을 타고 수평 속도를 얻어 나간다(사용자 실행 관찰, §2-4).
- 따라서 올바른 보정 프레임은 KLT 로컬도, MM base 반경 방향도 아닌 **스쿱(툴) 굴림
  방향**이다. Codex가 지시한 "KLT 로컬 고정 오프셋으로 교체"는 **전제가 틀렸다.**

→ **구현하지 않았다.** 대신 크기만 0.08 → 0.04로 줄여 벽 충돌을 없앴다.

## 1. 확인한 것 (bag `sim_diag_20260726_223158`, 1회차 플레이스 t≈140s)

### 1-1. 발행 슬롯 pose는 KLT 격자점과 일치한다

| 값 | 결과 |
|---|---|
| `/iw/basket/empty_slot_pose` (map) | (−0.1661, −9.3927, 0.5883) |
| 같은 시점 IW body pose | pos=(−0.0771, −9.5639), yaw=1.3451 rad |
| **슬롯 pose를 IW body 로컬로 역변환** | **(+0.1469, +0.1250)** |

`isaacpjt/robots/iwhub.py`의 KLT 격자는 `ox=(ix−1.5)×0.31`, `oy=(iy−0.5)×0.25`.

| 격자 후보 | 로컬 차이 |
|---|---|
| (ix=2, iy=1) → (+0.155, +0.125) | **(−0.008, +0.000)** ← 일치 |
| 그 외 7칸 | x 또는 y가 0.25~0.61 어긋남 |

y가 **정확히 0.0000** 일치한다. 남은 x −0.008m는 카고 루트가 IW body 원점 대비 갖는
고정 오프셋(`IW_LOAD_MAP_X_OFFSET_M` + chassis bbox 정렬)으로 설명된다.

### 1-2. 그 격자점은 “바구니 내부 중심”이다

`iwhub.py::load_cargo()`가 KLT를 배치하는 방식:

```python
kp = f"{load}/KLT_{ix}{iy}"
set_pose(stage.GetPrimAtPath(kp), (ox, oy, kz), ident)   # 시각 KLT
add_klt_shell(ix, iy, ox, oy)                            # 충돌 셸
```

그리고 `add_klt_shell(ix, iy, ox, oy)`는 바닥·4벽 콜라이더를 **모두 (ox, oy) 중심**으로
만든다. `Floor`는 `(ox, oy, …)`, `Wall_X_Neg/Pos`는 `ox ∓ inner_half_x`,
`Wall_Y_Neg/Pos`는 `oy ∓ inner_half_y`.

**과실을 실제로 받는 것은 이 콜라이더 셸이고, 그 내부 중심이 정확히 (ox, oy)다.**
발행 pose가 (ox, oy)와 일치하므로, 발행 XY는 이미 바구니 내부 중심이다.
여기에 8cm를 더 밀면 오히려 중심에서 벗어난다 — `inner_half_y`는 0.0741m라
**8cm는 내벽을 넘어간다.**

### 1-3. 파지 오프셋도 8cm를 설명하지 못한다

“TCP와 과실이 8cm 어긋나 있어 보정한다”는 대안 가설도 성립하지 않는다.
`mm.py::_publish_scoop_release()` 문서화된 실측값은 **GRASP 시점 과실–TCP 횡오프셋
0.9mm**다. 8cm와 두 자릿수 차이다.

수직 오프셋은 실재한다(`scoop_tip_below_tcp_m = 0.057`, 스쿱 메시 z 최대 177mm − TCP
120mm). 하지만 이는 z 전용 상수로 이미 따로 다뤄지고 있고, 이번 XY 보정과 무관하다.

## 2. 그래서 80mm는 무엇인가 — 확정

조사 시점에 세 가설을 세웠고, 이후 실행 관찰로 **가설 D가 확정**됐다(§2-4).

| # | 가설 | 판정 |
|---|---|---|
| A | 시각 KLT 메시 피벗이 콜라이더 중심과 어긋남 | 미확정(불필요) — 물리적으로는 콜라이더가 정답이고 그 중심이 발행된다 |
| B | map→base TF 오차가 8cm 수준으로 누적 | 부분 기여 가능. 안정화 검사 보강은 여전히 타당(§5) |
| C | 80mm가 경험적으로 맞춰진 값 | ✅ 맞다. 다만 무엇을 상쇄하던 값인지가 D |
| **D** | **스쿱 곡면 때문에 과실이 굴러 나가 낙하점이 릴리즈점과 다르다** | ✅ **확정 (§2-4)** |

### 2-4. 확정 — 스쿱 굴림 (2026-07-27 실행 관찰)

사용자 실행 관찰:

> 80mm: 과실이 **가장 가까운 두 바스켓 사이 벽 위**에 얹혔다.
> 40mm: 짧은 쪽 벽에 가깝긴 하지만 들어갔다. 그리고 **그리퍼가 굴곡져서 수직 낙하가
> 아니라 살짝 반포물선 낙하**가 된다.

이것으로 §1의 모순(발행 pose가 이미 내부 중심인데 왜 보정이 필요한가)이 풀린다.
스쿱은 동축 1/4구 셸이라 열리는 순간 과실이 곡면을 타고 **수평 속도를 얻어 나간다.**
그래서 TCP를 내부 중심에 두면 과실은 굴러간 만큼 벗어난 곳에 떨어진다.

- 보정 0 → 굴림만큼 벗어나 틈/벽 쪽으로 (Codex가 보고한 현상과 일치)
- 보정 80mm → 과보정으로 반대편 짧은 축 벽 위 (2026-07-27 관찰)
- 보정 40mm → 내부 착지

#### 왜 이 파라미터가 실행마다 다르게 동작했나
`basket_place_toward_mm_m`은 **MM base 원점 방향**으로 당긴다. 반면 굴림 방향은
스쿱 자세(joint_6 180° 회전 + 툴 자세)가 정하며 **KLT·base와 무관**하다.
두 방향이 우연히 맞으면 상쇄되고, 어긋나면 오히려 더한다.

실측 분해 (KLT 로컬):

| 실행 | KLT→MM 방향(로컬) | 80mm의 로컬 성분 | 결과 |
|---|---|---|---|
| bag 22:31 (슬롯 ix=2) | (+0.853, +0.522) | dx +0.068, dy **+0.042** | 내부(아슬아슬) |
| 23:xx 라이브 (앞열) | (+0.733, +0.680) | dx +0.059, dy **+0.054** | **벽 위** |

과실 반지름 0.034를 더하면 후자는 0.054+0.034 = **0.088 > 외벽 0.0842** → 벽을 타 넘는다.

#### 40mm의 근거
KLT 짧은 변(로컬 y) 내부 반폭 = `0.198 × 0.85 / 2 − 벽 0.010 = 0.0742`.
과실 반지름 0.034를 빼면 중심 허용 여유는 **±0.0402**.
→ 보정이 **전부** 짧은 축에 실리는 최악의 경우에도 `0.04 + 0.034 = 0.074 ≤ 0.0742`.
자세와 무관하게 벽을 타지 않는 상한이 0.04다. 회귀 테스트로 고정했다
(`test_basket_place_sequence.py`).

## 3. 남은 미측정 — 굴림 벡터 (필요해지면)

원인은 확정됐고 40mm로 동작하므로 발표 전 추가 측정은 필수가 아니다.
굴림을 **정량화**해 근본 대응(§7)으로 가려면 아래가 필요하다.

### 3-1. `release_debug`의 `fruit_map`
릴리즈 이벤트 분리 수정으로 이벤트 자체는 발행된다(실행 확인:
`{"seq":1,"fruit_id":61,...}`). **다만 `fruit_map`이 아직 `null`이다** —
`_ripe_by_id()` 또는 `_tcp_world()`가 실패한다. 이걸 고치면
`fruit_map − command_xy`가 **굴림 벡터 그 자체**가 되어 크기·방향을 직접 잰다.

```
publish_xy   = /iw/basket/empty_slot_pose (map)   ← KLT 내부 중심
command_xy   = 로그 "바스켓 릴리즈 XY: … → (x, y)"  ← 보정 후 TCP 명령
fruit_map    = /harvester_0/scoop/release_debug    ← 실제 낙하점 (현재 null)
```

### 3-2. 굴림 방향의 툴 프레임 성분
`fruit_map − command_xy`를 릴리즈 시점 TCP 자세로 역변환하면 툴 로컬 굴림 방향이
나온다. 이게 §7의 손목 정렬에 필요한 값이다.

## 5. 가설과 무관하게 지금 해도 되는 것

Codex 요청 7번(안정화 로직)은 **80mm의 정체와 무관하게 맞는 지적**이다.
현재 `_basket_callback`의 안정화 검사는 수신한 KLT의 **map XY만** 본다. MM base가
움직이거나 TF가 흔들려도 검출하지 못하고, 안정화 이후 들어온 pose가 진행 중인 place
목표를 바꿀 수 있다.

- base-frame 상대 XY도 함께 허용오차 안에 2초 유지되는지 검사
- 안정화 완료 시점 pose를 snapshot 해서 place 전체에서 재사용

이건 가설 B의 검출 수단이기도 하다. **먼저 이것만 구현할지** 지시 바란다.

## 6. 별건 — LIN 가속도 (사용자 지시로 적용 완료)

`mm_motion_bridge.py`의 `max_acceleration_scaling_factor` 0.30 → 0.25 → **0.22**.

`APPROACH → PREGRASP`의 Pilz LIN이 joint_4 한계(5.0) 초과로 궤적 생성에 실패했다.
스케일을 낮춰가며 실측한 위반값:

| scale | 실측 위반값 | 한계 대비 |
|---|---|---|
| 0.30 | −6.64159 / −6.53176 | 30% 초과 |
| 0.25 | −5.09777 / −5.0513 | 1~2% 초과 (여전히 실패) |
| **0.22** | 예상 4.5 | 통과 예상 — **미검증** |

선형 외삽 기준 필요값은 `0.25 × 5.0/5.098 ≈ 0.245` 이하다. 여유를 두고 0.22로 뒀다.
반영하려면 **`mm_motion_bridge` 노드 재시작이 필요하다**(실행 중 프로세스는 이미
로드한 코드를 쓴다).

> 참고: `[INFO] … RRTConnectkConfigDefault … will use planner 'geometric::RRTConnect'`는
> **오류가 아니다.** OMPL이 플래너를 알리는 정보 메시지이고 가속도와 무관하다.
> 실제 실패는 `[ERROR] pilz_industrial_motion_planner` 줄이다.

또한 재시도 로직이 **같은 표적을 4회 반복**했다. 기하학적으로 불가능한 자세면 반복해도
동일하게 실패한다 — 실패한 과실을 제외하고 다음 과실로 넘어가는 편이 2개 적재 성공률을
올린다. 이건 별도 판단이 필요해 손대지 않았다.

## 7. 근본 대응 (발표 후 검토 — 지금은 하지 말 것)

40mm는 "최악의 경우에도 벽을 안 타는 상한"이지 굴림을 상쇄하는 값이 아니다.
굴림 방향이 KLT 축과 무관하게 정해지는 구조 자체가 남아 있다.

**손목 회전각을 KLT 긴 축에 정렬한다.** KLT 여유는 축마다 두 배 차이다:

| 축 | 내부 반폭 | 과실 반지름 제외 여유 |
|---|---|---|
| 짧은 변(로컬 y) | 0.0742 | **±0.0402** |
| 긴 변(로컬 x) | 0.1162 | **±0.0822** |

지금 `BASKET_WRIST_ROTATE`는 joint_6을 **고정 180°** 돌린다. 이걸 발행 슬롯 pose의
orientation(이미 들어온다)과 §3-2의 툴 로컬 굴림 방향으로부터 계산해, 굴림이 **긴 축**을
향하게 하면 허용 여유가 두 배가 된다.

**발표 전에는 건드리지 말 것** — 손목 각도는 파지·후퇴 시퀀스와 얽혀 있고
(`_send_basket_wrist_rotate`가 joint_1~5 고정을 전제한다), 회귀 위험이 이득보다 크다.
