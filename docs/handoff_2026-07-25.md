### 플레이스 팔 경로

HOME을 먼저 거치면 바구니 방향과 `joint_1` 차이가 약 168°가 되어 IK 후보가
단일 관절 변화 제한 2.40rad에 모두 걸렸다. 현재 경로는 다음과 같다.

```text
픽 후 안전 후퇴
→ joint_1 유지, joint_2~6 접기
→ 접힌 상태에서 바구니 유무 판단
→ joint_1만 바구니 방위로 회전
→ 바구니 접근·릴리즈
→ 수직 후퇴
→ joint_1 유지, joint_2~6 고속 접기
→ 고속 HOME
```

`fold_keep_j1`은 최신 joint state가 없을 때 HOME으로 대체하지 않고 실패한다.
플레이스 후 접기와 HOME에만 속도 0.70, 가속도 0.50을 적용했다. 수직 후퇴는
15cm에서 8cm로 줄이고 LIN 속도를 0.45로 올렸다. 릴리즈 시 스쿱 최저점이 림보다
약 3cm 위이고, 후퇴 완료 시 약 11cm 위다.

### 최종 플레이스 좌표

- IW가 발행한 가장 가까운 KLT 중심을 사용한다.
- 최종 XY는 KLT 중심에서 수평면상 MM `base_link` 원점 방향으로 2cm 이동한다.
- `basket_place_toward_mm_m=0.02`
- `basket_approach_height_m=0.054`
- 슬롯 pose, TCP→스쿱 끝 오프셋을 반영한 목표 여유는 약 3cm다.
- 수확 자세를 재사용하지 않고 바구니용 하향 자세 `(x,y,z,w)=(1,0,0,0)`를 쓴다.

### KLT 물리

IW 팔레트 위 8개 KLT 각각에 바닥 1개와 벽 4개, 총 40개 analytic box collider를
생성한다.

- `UsdPhysics.CollisionAPI` 활성화
- `PhysxCollisionAPI` contact offset 2mm
- 바닥 collider 두께 30mm
- 벽 collider 두께 30mm
- 벽 안쪽 면과 KLT 내부 크기는 유지하고 바깥쪽으로만 확장
- 인접 KLT collider 간 최소 간격 X 17.55mm, Y 41.70mm
- 절단된 토마토에 CCD 활성화
- 생성 시 `KLT colliders=40/40, wall/floor=(0.030/0.030)m` 로그 검증

이 물리 변경은 USD stage 생성 시 적용되므로 반드시 Isaac Sim을 완전히 재시작해야
한다. 코드와 정적 기하는 검증했지만, 벽·바닥 관통 방지는 수정 후 새 녹화가 필요하다.

### MM 피항 뒤 IW가 출발하지 않은 원인

최신 녹화에서 신호 누락이 아니라 MM Nav2 목표 실패였다.

`MM_YIELDING_FOR_IW → WAITING_IW_RETURN → MM_CLEAR_TO_FORKLIFT`와 IW odom 이동을
확인해야 한다.

## 1. 현재 도달 상태

과거 통합 시험에서는 다음 흐름까지 확인했다.

```text
MM 자동 주행
→ 베드뷰·토마토 선택
→ APPROACH / PREGRASP / GRASP
→ 파지 검증·절단
→ RETRACT
→ IW FOLLOW·비접촉 도킹
→ BASKET_APPROACH
→ BASKET_PLACE
→ 그리퍼 개방
→ BASKET_RETRACT
→ GO_HOME
```

즉, 수확부터 바스켓 플레이스 릴리즈까지 제어 시퀀스는 연결된 이력이 있다.

최신 녹화 `sim_diag_20260725_143744`에서는 다음 흐름을 다시 확인했다.

```text
MM 자동 Nav2 → HOME → BED_VIEW
→ APPROACH / PREGRASP / GRASP
→ 파지 검증·절단
→ RETRACT_CIRC / RETRACT_LIN
→ WAIT_BASKET
```

이 녹화에서 플레이스로 넘어가지 않은 직접 원인은
`/iw/basket/empty_slot_pose`가 1,800회 발행됐지만 모두 빈
`PoseStamped(frame_id="", xyz=0)`였기 때문이다. 최종 원인은 실제 KLT가
`/World/IwHubCargo/Pallet_00/KLT_*` 아래에 있는데 pose publisher가 이전
`/World/IwHubCargo/Load/KLT_*` 경로를 조회한 것이었다. 활성 IW 적재물 경로를
`Pallet_00`으로 통일하고, 실제 KLT prim 중 MM에 가장 가까운 슬롯의 release pose를
`map` 프레임으로 한 번만 발행하도록 중복 선택 로직도 제거했다.

`sim_diag_20260725_150807`에서 이 수정의 적용은 확인됐다.

- `/iw/basket/empty_slot_pose`: `frame_id="map"`, 약 `(0.008, -10.543, 0.589)`
- 같은 점의 MM `base_link` 변환값: 약 `(-2.09, +0.95, 0.29)m`
- 현재 허용 작업영역: `[-0.80, -0.80, 0.15] .. [1.35, 0.80, 1.80]`
- 결과: `작업영역 밖 바스켓 목표를 무시합니다`가 반복되어 `WAIT_BASKET` 정지

즉 pose 발행과 `map → harvester_0/base_link` 변환은 정상이다. 남은 직접 원인은
IW FOLLOW가 `dock_standoff=1.2`를 **IW 차체 중심 기준**으로만 맞추며, 실제 팔이
접근해야 하는 KLT release pose는 MM에서 약 2.3m 떨어져 있다는 점이다.

이후 작업영역 밖 슬롯을 받으면 무한 대기하지 않고, 그리퍼를 닫은 채 즉시
`GO_HOME → HOME_READY`로 복귀하도록 수정했다. 이 HOME fallback은 빌드됐지만
실제 녹화로는 아직 검증하지 않았다.

플레이스 시험에서는 토마토가 빈 KLT를 통과했다. 원인은 릴리즈 위치나 토마토
RigidBody가 아니라, 초기 토마토가 들어 있는 KLT에만 collider가 있고 빈 플레이스
대상 `KLT_31`에는 collider가 없었던 것이다.

수정 사항:

- KLT 8개 모두에 바닥과 4개 벽으로 구성된 열린 상자 collider 적용
- `filled`는 초기 토마토 생성 여부만 결정하도록 분리
- Python 문법 검사, deck geometry 테스트 5개, diff 형식 검사 통과

**아직 수정 후 실제 플레이스 재시험은 하지 않았다.**

## 2. 다음 작업 우선순위

### 1순위 — IW FOLLOW 목표를 실제 KLT 기준으로 수정

현재 가장 먼저 해결할 항목이다. `mission_nav_node._follow_target()`은 MM과 IW
차체 중심 사이 거리만 1.2m로 맞춘다. 이 방식으로는 IW Nav2가 성공해도
`Pallet_00/KLT_*`가 팔 작업영역에 들어오지 않는다.

수정 원칙:

- 단순히 `basket_workspace_min/max`를 넓히지 말 것. 실제 팔 도달거리 밖이다.
- IW 차체 중심 대신 실제 선택 KLT release pose가 MM `base_link` 작업영역에
  들어오도록 FOLLOW 최종 자세 `(x, y, yaw)`를 계산할 것
- KLT 적재면이 MM을 향하도록 IW 최종 yaw도 함께 결정할 것
- 베드·MM·IW footprint 비접촉 조건을 유지할 것
- FOLLOW goal 성공과 KLT pose 도달 가능 판정을 별도로 로그/상태로 남길 것

최신 실패 수치:

```text
MM base origin(map) ≈ (-0.439, -8.292, 0.300)
선택 KLT release(map) ≈ (0.008, -10.543, 0.589)
release in MM base ≈ (-2.091, +0.946, 0.289)
허용 x/y = [-0.80, 1.35] / [-0.80, 0.80]
```

### 2순위 — KLT 물리 수정·실제 플레이스 재검증

Isaac Sim을 완전히 재시작한 뒤 통합 시험을 다시 실행한다.

확인할 것:

- 플레이스한 토마토가 `KLT_31`을 관통하지 않는가
- KLT 바닥에 정상 안착하는가
- IW가 출발하거나 회전할 때 KLT 밖으로 튀지 않는가
- KLT 8개의 상자 collider 추가로 physics frame rate가 크게 저하되지 않는가

### 3순위 — 플레이스 위치 미세조정

현재 바스켓 목표는 MM과 가장 가까운 앞쪽 빈 슬롯을 선택하고, release 목표를 MM
쪽으로 `0.02 m` 당긴다.

- 파라미터: `basket_place_toward_mm_m=0.02`
- 슬롯: 실제 KLT prim 중 현재 MM에 가장 가까운 슬롯을 동적으로 선택
- release 높이: KLT 윗면보다 `0.05 m`

물리 collider 적용 후 토마토가 벽이나 슬롯 사이에 떨어진다면 시각 관찰을 기준으로
`basket_place_toward_mm_m`을 조정한다.

### 4순위 — 연속 플레이스

현재 8개 KLT는 모두 빈 상태로 시작하며, pose publisher는 점유 상태를 갱신하지
않고 매 프레임 MM과 가장 가까운 KLT를 반복 선택한다.

연속 수확을 구현하려면:

- 플레이스 완료 후 슬롯 점유 상태 갱신
- 다음 빈 슬롯 선택
- 뒤쪽 슬롯까지 사용할 경우 MM 작업영역과 팔 도달성 재검증
- KLT별 토마토 개수 또는 점유 판정 방식 결정

### 5순위 — MM 피항·IW 하역 핸드셰이크 재검증

적재 완료 뒤 IW가 중앙 하역 레인으로 출발할 때 MM이 길을 막지 않도록 다음
핸드셰이크를 추가했다.

```text
MM HOME_READY + 플레이스 완료
→ /iw/mission=PREPARE_FORKLIFT
→ IW 정지 + /iw/mm_yield_request=True
→ MM 피항 Nav2: (-0.8, -6.8, yaw=0)
→ MM 상태 WAITING_IW_RETURN
→ /iw/mm_yield_complete=True
→ IW FORKLIFT 전환·하역 출발
```

피항 중 팔 HOME, MM Nav2 준비, 목표 수락·성공을 모두 확인한다. 실패하면
`mm_yield_complete=True`를 보내지 않으므로 IW는 출발하지 않는다.

실제 통합 시험에서 확인할 것:

- IW가 `PREPARE_FORKLIFT` 동안 정지하는가
- MM 피항 경로가 베드 및 정지 중인 IW와 충돌하지 않는가
- MM이 피항 완료 후 추가 수확 없이 `WAITING_IW_RETURN`으로 대기하는가
- 완료 신호 전에는 IW가 하역 경로를 시작하지 않는가

### 6순위 — IW 주행 안전장치

아직 미구현:

- cmd_vel은 존재하지만 odom 이동이 거의 없는 상태를 감지하는 stuck watchdog
- 정지 후 후진·재계획 복구
- 장애물 거리별 강제 감속·정지용 Nav2 Collision Monitor

### 7순위 — 동시 기동 안정성

현재 IW localization은 지연 기동과 lifecycle activator로 보완했다. 하지만 MM
MoveIt, MM Nav2, IW Nav2 동시 기동 시 DDS 응답 유실 가능성이 완전히 제거된 것은
아니다.

후보:

- MM Nav2와 IW navigation에도 동일한 lifecycle 상태 확인·재시도 적용
- FastDDS Discovery Server 도입 검토
- RViz 기동 지연 또는 분리 실행으로 Isaac과 GPU/OpenGL 경합 완화

## 3. 실행 방법

### 분리 실행(현재 권장)

분산 배포를 준비하기 위해 `smartfarm_bringup` 패키지를 추가했다. Isaac은 하나의
USD 물리 월드를 소유하므로 한 프로세스에서 세 로봇을 만들고, ROS 판단 스택은
MM/IW/지게차별로 분리한다.

```bash
# GPU/Isaac 호스트
ros2 launch smartfarm_bringup isaac_sim.launch.py

# ROS 호스트 — 각각 별도 터미널/호스트 가능
ros2 launch smartfarm_bringup mm.launch.py
ros2 launch smartfarm_bringup iw.launch.py
ros2 launch smartfarm_bringup forklift.launch.py
```

`mm.launch.py`는 MoveIt, MM Nav2, 비전, 수확 코디네이터를 함께 자동 기동하고
MoveIt 준비 신호를 확인한 뒤 고정 수확 목표 `(-0.54, -8.19, yaw=1.91)`를 자동
전송한다.

## 6. 기동 안정화·MoveIt 준비 게이트

`sim_diag_20260725_141821`에서는 MoveIt 구성 일부와 controller는 보였지만
`rmp_home` 이후 `GO_HOME` 응답이 없었다. 브리지 큐의 joint state 조건은
충족됐으므로 `move_action` discovery가 막힌 것으로 판정했다.

적용 사항:

- `mm_motion_bridge`가 latched `/harvester_0/moveit_ready` 발행
- action 서버 미발견 10초 후 `ERROR_MOVEIT_UNAVAILABLE` 진단
- action discovery를 계속 재시도하고 연결 복구 시 자동 진행
- MM 코디네이터가 MoveIt 준비 전 자동 Nav/팔 시퀀스를 시작하지 않음
- controller spawner 서비스 응답 유실 시 재시도 대기를 60초에서 8초로 단축

실제 후속 실행에서는 controller 응답 한 번이 유실됐지만 MoveIt이 뒤늦게 자동으로
기동했고, 자동 Nav 목표와 HOME/BED_VIEW까지 진행했다. 8초 설정은 다음 재시작부터
검증해야 한다.

## 7. IW FOLLOW 회전 수정

최신 녹화에서 IW는 중앙 레인 `x=0`을 따라온 뒤 정확한 standoff 목표
`(0.2, -9.3)`로 가기 위해 마지막 20cm 횡이동과 90° 회전을 수행했다. 짧은 구간
때문에 코너 반경이 약 9cm로 줄어 DWB가 제자리 회전으로 처리한 것이다.

수정:

- FOLLOW에서 `snap_target_x=True`
- 최신 녹화 조건의 최종점: `(0.0, -9.3, yaw=90°)`
- MM과 실제 거리 약 1.23m로, 설정 1.2m 대비 약 3cm 오차
- 해당 경로 13 waypoint, 최대 간격 0.484m, footprint 충돌 검사 통과

전체 `test_lanes.py`는 11개 중 10개 통과했다. 실패 1개는 이번 FOLLOW 조건이 아니라
배드 구간에서 중앙 레인보다 18cm 벗어난 기존 시작 자세 케이스이며 별도 수정이
필요하다.

## 8. 코드상 주의사항

- 현재 일체형/분리형 런치는 모두 `dock_standoff=1.03` 기준이다.
- KLT pose 선택은 현재 1개 적재 후 바로 하역하는 시나리오에 맞춰 매번 MM과 가장
  가까운 슬롯을 선택한다. 연속 적재 전에는 슬롯 점유 관리가 필요하다.
- `WAIT_BASKET`에서 변환된 슬롯이 MM 작업영역 밖이면 더 이상 무한 대기하지 않고,
  그리퍼를 닫은 채 `GO_HOME`으로 복귀한다. IW 도킹 목표는 차체 중심이 아니라 실제
  KLT release pose가 팔 작업영역에 들어오도록 후속 보정이 필요하다.
- MM 피항 위치는 최신 녹화에서 실제 도달한 `(-0.8, -6.8)`로 변경했으며,
  Nav2 성공과 IW 출발까지는 새 통합 검증이 필요하다.
- 새 KLT pose publisher는 Isaac 코드이므로 Isaac을 완전히 재시작해야 적용된다.
- 피항 핸드셰이크는 MM/IW ROS 노드를 모두 재시작해야 적용된다.
- `src/smartfarm/INTERFACES.md`의 IW Nav2 미구현 설명은 과거 상태일 수 있으므로
  실행 코드와 `iw_current_branch_reference.md`를 현재 기준으로 사용한다.
